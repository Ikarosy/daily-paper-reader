## 摘要
在基于暂存式张量加速器（STA）上的混合专家（MoE）解码中，主要开销来自搬运专家权重，而计算引擎处于空闲状态。这种流量很难被掩盖，因为只有在路由之后才知道使用了哪些专家；同时，也很难在不损失质量或不增加关键路径工作的情况下将其缩减。我们提出 CARDAN，它将每个专家权重矩阵表示为向量量化分量加共享基低秩分量，并将该表示与多引擎解码数据流进行协同设计。该表示将专家共有工作与专家私有工作分离，因此数据流可在多个引擎上将 DMA 与计算重叠。在 AWS Trainium3 上的五个 MoE 系列中，CARDAN 在全部五个模型上匹配或改善了 BF16 教师模型的困惑度，并将批量大小为 1 的解码相比 AWS 稠密 MoE 巨型内核加速 1.15–1.31 倍，在批量大小为 16 时提升至 1.7 倍。

## Abstract
Mixture-of-Experts (MoE) decoding on scratchpad-based tensor accelerators (STA) is dominated by moving expert weights while the compute engines sit idle. This traffic is hard to hide, because the experts are known only after routing, and hard to shrink without losing quality or adding critical-path work. We present CARDAN, which represents each expert-weight matrix as a vector-quantized component plus a shared-basis low-rank component and co-designs this representation with a multi-engine decoding dataflow. The representation separates expert-common from expert-private work, so the dataflow overlaps DMA with computation on several engines. Across five MoE families on AWS Trainium3, CARDAN matches or improves BF16-teacher perplexity across all five models and speeds up batch-one decoding by 1.15-1.31x over AWS dense MoE megakernels, rising to 1.7x at batch size 16.

## 1. 核心问题与研究动机

- **背景**：MoE 通过稀疏路由（每 token 只激活少量专家）扩大参数容量而保持每 token FLOPs 近乎不变，已成为前沿模型的主流架构。暂存式张量加速器（STA，如 AWS Trainium、Google TPU、Intel Gaudi 2、Huawei Ascend）使用软件显式管理的 Scratchpad Memory（SPM）而非硬件缓存，以 DMA 在 HBM 与 SPM 之间搬运张量。
- **核心瓶颈**：MoE **解码**（decode）阶段是访存受限的，端到端延迟被**专家权重搬运**主导，而多个异构计算引擎大量空闲。
  - 以 Qwen3-30B-A3B 为例：48 层，每层从 128 个专家中激活 8 个，BF16 下每层每 token 产生约 75 MB 权重流量。
  - 实测（图 1，TP=4，Trainium3）：Qwen3 中专家权重加载占端到端延迟 **56.0%**，其中 **36.8%** 暴露在关键路径；Gemma-4 关键路径暴露占 **42.5%**，Nemotron-3 占 **30.5%**。同时 SIMD 引擎仅活跃 4.1–4.7%，向量引擎仅 7–10.1%。
- **两大挑战**：
  1. **流量难隐藏**：只有路由之后才知道选中哪些专家，预取机会有限；已有基于激活历史的预取方案（SiDA、Pre-gated MoE、MoE-Infinity、ProMoE）在 STA 上失效，因为预取会在有限的 SPM 中制造长生命周期缓冲，且编译器可能回收/覆写预取专家的内存，使预取失效并浪费搬运。
  2. **流量难压缩**：稀疏张量格式等会破坏 DMA 的规则性——DMA 服务时间不仅取决于字节数，还取决于包数量、地址规整性与传输串行化；更小的存储格式不必然带来等比例的 DMA 时间下降。VQ 虽可减小流量，但需要为每个专家存索引图并做码字选择，实测在 Trainium 上可占端到端解码延迟的 **20%**。
- **整体含义**：作者主张**为 STA 定制专家权重表示**，并与执行数据流协同设计，是同时解决数据搬运与引擎闲置问题的关键；把"模型表示"与"加速器数据流"围绕关键路径、搬运、SPM 驻留、异构引擎工作与同步一起设计。

## 2. 方法论（CARDAN）

### 2.1 核心思想：混合专家权重表示（VQ + 低秩）

- 每个专家的 gate/up 投影权重矩阵表示为**向量量化分量 + 共享基低秩分量**之和：
  - **公式**：`o_e = W_e^T h ≈ Ŵ_e^T h = Q_B(J_e)^T h + C_e^T (D^T h)`
    - 第一项为 VQ 项：`Q_B(J_e)` 由专家私有索引图 `J_e` 在共享权重码本 `B` 中查表得到；
    - 第二项为 LR 项：`D` 为层内所有专家共享的秩-r 基张量，`C_e` 为专家私有系数矩阵。
  - **共享/私有划分**：`B`（码本）与 `D`（基）层内共享、每 token 只加载一次；每个被激活专家只需额外搬运其 `J_e` 与 `C_e`。
- **为什么二者互补**（图 5）：
  - LR 单独使用会严重掉质量：Qwen3-30B-A3B 的困惑度从 9.82 恶化到 **34.91**（+255.4%），因为私有系数只能给出低秩近似，丢失专家特有信息。
  - 约 4 bits/weight 时输出 NMSE：LR only 13.46%，VQ+LR **5.72%**，VQ only（d=2）1.62%；LR only 在 8 bits 的 6.98% 仍差于 VQ+LR 在 3 bits 的 6.73%。
  - VQ 单独要达到同等精度必须把块长 `d` 调小，而 `d` 每减半就使索引选择次数翻倍，把开销压到关键路径上；因此用 LR 补足质量后，VQ 可用更粗粒度的码字以降低运行时开销。
- **不压缩 down 投影**（保持 BF16），原因有二：(1) 所有被激活专家对同一 `h` 做 gate/up 投影，共享 `B`/`D` 的工作可复用，而 down 投影接收的是各专家私有的中间激活 `p_e`，套用 VQ+LR 会为每个专家重复乘不同 `p_e`；(2) down 投影权重 **超过 80%** 的 DMA 时间已与 gate/up 计算重叠，关键路径上剩余很少。

### 2.2 引擎分工与互补

- **LR** 部分：`z = D^T h` 每 token 一次，`C_e^T z` 每专家一次，均为密集矩阵-向量乘，放在**张量引擎**。
- **VQ** 部分：每个权重块一次索引选择（`nc_n_gather`），彼此独立、计算量小，放在 **GpSimd**。
- 两者无相互依赖，

- 两者无相互依赖，因此可以**并行发射**：GpSimd 上的索引选择（`nc_n_gather`）与张量引擎上的 LR 基变换 `D^T h` 在时间上重叠，把 VQ 的运行时开销从关键路径上"藏"起来。索引选择只读取专家私有的 `J_e`，LR 只读取共享的 `D`，二者不争抢同一数据，也不产生顺序约束。

- **三条并行轨**（作者据此把解码层切成可重叠的流水）：
  1. **共享轨**：每 token 加载 `B` 与 `D`，并计算 `z = D^T h`（张量引擎）；
  2. **VQ 轨**：每个被激活专家加载 `J_e`，GpSimd 做块级码字选择，张量引擎随后算 `Q_B(J_e)^T h`；
  3. **LR 轨**：每个被激活专家加载 `C_e`，张量引擎算 `C_e^T z`，与 VQ 项相加得到 gate/up 输出 `o_e`。

- **关键设计收益**：把"每专家一份大权重"替换为"每 token 一份共享码本/基 + 每专家一份小索引/系数"，使得**共享部分随 token 摊销、私有部分随专家摊销**。这既降低了总搬运字节，也把搬运从"大块连续"变成"小块规整"，避免了稀疏格式对 DMA 规则的破坏。

### 2.3 与 STA 执行模型的协同（数据流调度）

- **SPM 驻留策略**：`B` 与 `D` 是层内共享、每 token 复用的对象，被显式钉在 SPM 中，token 之间不重搬；`J_e`、`C_e` 是专家私有、按路由结果动态加载，避免长生命周期预取缓冲——这正回应了"预取在有限 SPM 中制造长缓冲、且被编译器回收"的失效机理。
- **规避预取失效**：不依赖激活历史做投机预取，而是把"减少关键路径搬运量"作为第一性目标；路由确定后再加载 `J_e`/`C_e`，但由于其体积远小于原始 BF16 专家权重，暴露的搬运时间被压缩。
- **DMA 友好性**：索引图与系数矩阵按规整块布局，使 DMA 服务时间更接近字节数比例，而非受包数与地址碎片支配；这与 2.1 中"更小格式不必然等比例降低 DMA 时间"的观察直接对应。
- **异构引擎负载均衡**：把 SIMD/GpSimd 从近空闲状态（原先 4.1–4.7%）提升为承担索引选择，向量引擎承担部分轻量运算，从而让张量引擎专注密集矩阵-向量乘，缓解"多引擎空闲而关键路径堵在搬运"的结构性错配。

### 2.4 关键路径上的取舍

- **只压缩 gate/up、保留 down 为 BF16**：如 2.1 所述，down 投影的私有激活 `p_e` 使 VQ+LR 无法复用，且其超过 80% 的 DMA 时间已与计算重叠，压缩收益边际小、复杂度高。
- **码字粒度 vs 精度 vs 开销的三方权衡**：粗码字降低索引选择频率但损失精度，LR 项用来补足这部分精度缺口，使 VQ 可以停留在较低选择频率；这是一种把"表示精度"与"运行时开销"解耦的设计，而非单纯追求最小比特数。

## 3. 实验评估（要点）

- **平台与模型**：在 Trainium（TP=4）上，针对 Qwen3-30B-A3B、Gemma-4、Nemotron-3 等 MoE 模型进行解码阶段评测。
- **端到端收益方向**：
  - 权重搬运量与关键路径暴露时间显著下降，缓解了 36.8%（Qwen3）、42.5%（Gemma-4）、30.5%（Nemotron-3）的关键路径暴露问题；
  - 消除了 VQ 单独使用时可达约 20% 端到端延迟的索引开销（通过引擎重叠与 LR 补偿）；
  - 质量侧以困惑度/NMSE 为指标，VQ+LR 在约 3–4 bits/weight 下明显优于任一单独方案（如 VQ+LR 5.72% vs LR-only 13.46% 的 NMSE）。
- **消融维度**：VQ-only、LR-only、VQ+LR 的质量—开销对比；是否压缩 down 投影；引擎分工与重叠对关键路径的影响；码字粒度 `d` 的敏感性。

## 4. 讨论与局限

- **适用边界**：方法依赖"层内专家共享码本/基"的结构性假设，对专家异质性极强、或共享基难以覆盖的层，LR 项的补偿能力可能受限。
- **编译/运行时耦合**：需要编译器与运行时对 SPM 驻留、DMA 布局、多引擎同步提供细粒度支持，落地依赖特定 STA 工具链。
- **精度—压缩的连续谱**：`d`、秩 `r`、码本大小构成多维权衡，需针对不同模型与延迟预算调参。
- **可推广性**：思路（共享+私有分解 + 引擎互补 + 关键路径优先）原则上可迁移到其他访存受限的稀疏/大权重场景。

## 5. 结论

CARDAN 的核心主张是：**为 STA 定制专家权重表示，并与执行数据流协同设计**。它以 VQ+LR 混合表示在质量与压缩率间取得更优折中，以共享/私有划分摊薄搬运，以张量引擎与 SIMD 引擎的互补分工把索引选择移出关键路径，并以"只压 gate/up、保护 down"的取舍聚焦真正的瓶颈。其价值不在于单点压缩技巧，而在于把表示、搬运、SPM 驻留、异构引擎工作与同步围绕解码关键路径统一设计。
