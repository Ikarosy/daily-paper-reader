## Abstract 

SSD-resident approximate nearest-neighbor search is essential when vector collections exceed DRAM capacity. The challenge is to reduce SSD reads and hide I/O latency through concurrent reads and overlap with computation. However, for graph-based search, progressive candidate discovery limits advance I/O planning while IVF search reads inverted lists in full, incurring unnecessary SSD reads. In this paper, we present RaBitQ-SSD, an extension of IVF-RaBitQ for SSD-resident vector search. Specifically, we propose Split-RaBitQ, which retains a configurable prefix of each binary code in DRAM, allowing in-memory code storage below one bit per dimension. Using this partial representation, it provides an unbi-ased distance estimator with a probabilistic error bound. Once the in-memory coarse quantizer identifies candidate lists, this bound supports pruning individual candidates within them, enabling finer-grained SSD access. We also design an asynchronous search pipeline that coordinates candidate pruning with SSD read scheduling to reduce unnecessary reads while overlapping I/O with computation. On datasets ranging from 5 million to 1 billion vectors, RaBitQ-SSD delivers up to 1 .74 × the throughput of graph-based baselines at 90% recall, while reducing SSD page reads by up to 3 .8×. Its on-SSD indexes are up to 7 .0× smaller and 10 .0× faster to build than DiskANN. We also build and search an index of 10 billion vectors on a single machine with one SSD, achieving over 3 ,000 queries per second at 90% recall. 

## 1 Introduction 

Modern embedding models represent unstructured data, such as images and text, as high-dimensional vectors, typically with hun-dreds to thousands of dimensions. Approximate nearest-neighbor (ANN) search retrieves vectors close to a query without exhaus-tively scanning the collection and underlies applications such as semantic search, recommendation, and retrieval-augmented gener-ation [32, 43]. As collections grow, however, the vectors themselves can exceed the memory capacity of a single machine: one billion 1024-dimensional vectors in FP32 already occupy 4 TB. Flash stor-age provides a natural storage tier for such collections: modern flash-based SSDs offer roughly 10–50 × lower cost per byte than DRAM and a single PCIe 4.0 NVMe SSD can deliver over one mil-lion random-read IOPS [25]. DiskANN [53] established a widely adopted graph-based design for SSD-based ANN search in which compact quantized codes in DRAM guide the search while the graph and full-precision vectors reside on SSD. Its synchronous beam search batches reads to exploit device parallelism, but each search round waits for those reads to complete before the next round, limiting I/O–computation overlap. Starling [63] reduces SSD I/O through locality-aware graph reorder-ing and shorter traversal paths. However, as vector dimensionality grows and vertex records become larger, fewer related vertices can be co-located within the same SSD block. PipeANN [22] breaks the strict compute–I/O ordering of conventional beam search by spec-ulatively issuing reads while computation proceeds. However, later I/O completions may reveal better candidates, making some specu-lative reads unnecessary. Subsequent work further optimizes disk layouts and caching [30, 34, 42, 75], the placement of compressed codes [44, 54, 73], distance computation [10], and I/O–computation scheduling [31]. Despite these optimizations, graph methods with SSD-resident adjacency lists retain a structural constraint: candi-dates are discovered progressively as the traversal proceeds. On the other hand, IVF-based indexes organize vectors into inverted lists, avoiding the cost of building and storing a proximity graph over the full collection. An in-memory coarse index identifies candidate lists before accessing their SSD-resident contents. Among these methods, SPANN [9] uses query-aware pruning to select inverted lists, while HELMSMAN [27] learns how many lists to probe. Both read the selected lists in full from SSD. This motivates finer-grained I/O pruning within probed inverted lists. If an in-memory representation provides distance estimates with lower bounds for each vector, the bounds can help rule out vectors that cannot improve the current 𝑘 NN result before fetching their SSD-resident data. The in-memory IVF-RaBitQ [16, 17, 59] supports such error-bounded pruning by maintaining two repre-sentations of each vector. This separation naturally sug-gests an SSD-based extension: retain the compact codes in DRAM for pruning and place the higher-precision representations on SSD for re-ranking, but this exposes two challenges. First, this direct extension retains the full binary code and cannot accommodate memory budgets below one bit per dimension that is necessary on billion scale datasets, e.g., for 10 billion 1024-dimensional vectors, the binary codes alone require about 1.28TB of DRAM. Second, the in-memory pruning needs careful coordination with I/O pipelining so as to reduce unnecessary reads and enable I/O–computation overlap, e.g., fetching the candidates surviving the pruning individ-ually wastes page bandwidth, issuing pages too early can read data that later pruning would eliminate, etc. In this paper, we present RaBitQ-SSD, an SSD-based extension of in-memory IVF-RaBitQ that addresses these two challenges. First, we propose Split-RaBitQ (§3), which keeps only a prefix of 𝐷 𝑚 ≤ 𝐷 

bits of each binary code in memory. Therefore, the memory con-sumption is configurable by setting 𝐷 𝑚 . We derive an unbiased distance estimator and a corresponding error bound from the prefix alone, enabling error-bounded pruning. Second, we develop an asyn-chronous SSD search pipeline that reduces SSD reads while overlap-ping I/O with computation. The pipeline coalesces surviving can-didates at page granularity and issues page reads asynchronously under a bounded in-flight I/O budget. It prioritizes more promising pages and re-evaluates them against the latest distance threshold before issuance, allowing updated search results to eliminate many unnecessary SSD reads without sacrificing I/O concurrency. In summary, we make the following contributions. 

• We propose Split-RaBitQ (§3), which keeps a configurable prefix of each RaBitQ binary code in DRAM. We derive an unbiased distance estimator and a probabilistic error bound from the prefix, enabling candidate pruning with an in-memory code footprint below one bit per dimension. 

• We design an asynchronous search pipeline (§4) that reduces unnecessary SSD I/O while sustaining I/O– computation overlap. 

• We conduct an extensive evaluation of RaBitQ-SSD (§5) on six datasets ranging from 5M to 1B vectors and 512–1536 dimensions, comparing against strong baselines. We further evaluate scalability from 100 thousand to 10 billion DINO vectors on a single server with one SSD (Figure 1). RaBitQ-SSD is open-sourced at https://github.com/VectorDB-NTU/RaBitQ-SSD. 

## 2 Preliminaries 2.1 ANN Search and IVF 

Let X ⊂ R𝐷 be a collection of 𝑁 data vectors, and let 𝑞 𝑟 ∈ R𝐷 

be a query vector. Given a distance function, a 𝑘 -nearest-neighbor (𝑘 NN) query asks for the 𝑘 vectors in X closest to 𝑞 𝑟 . In large-scale vector search, this query is typically answered approximately and thus is called approximate nearest neighbor (ANN) query: an ANN algorithm returns a set R of 𝑘 vectors, whose accuracy is measured by recall@ 𝑘 = |R ∩ G|/ 𝑘 , where G denotes the exact 𝑘 NN set. The inverted file (IVF) [28] is a classical partitioning-based ANN index that underlies many widely deployed vector search sys-tems [11, 61, 65]. At build time, the dataset is partitioned into 𝑛 list 

clusters, typically by 𝑘 -means. The centroids 𝑐 1, . . . , 𝑐 𝑛 list serve as a coarse quantizer, each vector being assigned to its nearest centroid, and the vectors assigned to 𝑐 𝑖 form the inverted list 𝐿 𝑖 . At query time, IVF scans the 𝑛 probe lists whose centroids are closest to 𝑞 𝑟 , in ascending order of centroid distance; the parameter 𝑛 probe controls the accuracy–efficiency trade-off. Though IVF narrows the search to the probed lists, scanning a list still requires estimating the dis-tance from 𝑞 𝑟 to every vector in it, so fast distance estimation with a small memory footprint is crucial. It can be achieved through vector quantization such as RaBitQ [16, 17], which we review next.

## 2.3 In-Memory IVF-RaBitQ and a Naive SSD Extension 

The in-memory IVF-RaBitQ [16, 17, 59] integrates Extended Ra-BitQ into an in-memory IVF index. Each inverted list stores the binary codes of its vectors packed in batches of 32 for FastScan. The search maintains KNNSet , the 𝑘 candidates with the smallest refined distances found so far. The threshold dist 𝑘 is the largest of these distances, or +∞ before 𝑘 candidates have been collected. In a probed list, every batch yields estimates and lower bounds (for batches of 32 candidates). Candidates with LB (𝑞 𝑟 , 𝑜 𝑟 ) < dist 𝑘 are re-ranked using their ex-codes and may update KNNSet; all others are pruned. No raw vectors are kept; the refined distances are used for the final ranking [16]. The most direct way to port this index to SSD, suggested in [16], keeps the binary code and the three factors in memory, and moves the ex-codes, with their two re-ranking factors, to SSD. The search is unchanged up to re-ranking: when a candidate survives pruning, the page holding its ex-code is read from SSD, scanning blocks until the read completes, and the candidate is re-ranked. However, this naive extension has two problems. 

Problem 1: a rigid memory footprint. The binary code has a fixed size, one bit per coordinate, so the in-memory part of the index occupies 𝑁 𝐷 /8 bytes plus the factors, which is over 1TB when 𝑁 

is 10 billion and 𝐷 = 1024. In this paper, we present Split-RaBitQ (§3), which keeps only a prefix of the binary code in memory, and show that the prefix still yields a lower bound for pruning. As a result, the size of the in-memory code is configurable by setting the length of the prefix. 

Problem 2: blocking I/O. A random SSD read of 4 KB typically takes 10s of microseconds. Issuing one read at a time therefore completes ∼10k of reads per second, far below the 1M+ 4 KB ran-dom reads per second that an SSD can sustain [25]. Reaching this throughput requires hundreds of concurrent outstanding requests. Instead of blocking on every read in the naive extension, we de-velop an asynchronous pipeline (§4) that overlaps I/O with the computation of scanning the codes in memory. 

## 3 Split-RaBitQ 

Split-RaBitQ, resolves Problem 1 by splitting the binary code be-tween memory and SSD: §3.1 gives the design, and §3.2 derives the lower bound and its guarantee from RaBitQ’s analysis.

## 4 Search Pipeline 4.1 Overview 

Figure 2 gives an overview of the search pipeline. 

Storage. The in-memory coarse quantizer routes a query to its 

𝑛 probe nearest clusters. Each cluster stores, for every vector, the 𝐷 𝑚 -bit prefix of its binary code together with its three factors (§3.1), stored in batches of size 32. The SSD holds one fixed-size record per vector, consisting of the suffix bits of the binary code, the ex-code, and the two re-ranking factors. The records of a cluster are packed into contiguous 4 kB pages (§2.3), with some padding so that they don’t cross page boundaries. The in-RAM and SSD vectors are stored in the same order (by ascending distance to the centroid), so that the page containing a record can be determined directly. 

Searching. ## 4.3 Pipelining the Inverted-List Search 

RaBitQ-SSD scans the 𝑛 probe inverted lists, for which we design several pipelines of increasing complexity, starting from the naive extension of §2.3. See Table 1 for the experimental setup and I/O numbers cited below. 

Naive . The naive extension of §2.3 issues one read per surviving candidate and blocks on it. It has one virtue: every pruning decision sees the tightest dist 𝑘 available so far, because it is fully causal. The query thread, however, waits out every read: a query issues 102 page reads at 𝑘 =10 and 614 at 𝑘 =100 on average, each delivering one useful record out of the three a page holds, and the thread waits on I/O for 95–99% of the list-search time (Table 1). 

Coalesced . Points of the same page that survive pruning can share one read ( 3○ in Fig. 2): because the scan visits the points of a page consecutively (§4.1), the surviving points of a page emerge con-secutively, and its read is issued when the scan crosses the page boundary. The speedup is due to fewer page reads: for 𝑘 = 10, 102 reads per query become 81, or 1 .30 × throughput (1 .66 × throughput for 𝑘 =100). The tightest-threshold property of Naive is preserved at page granularity. 

Overlapped . Blocking is what stalls the query thread (the grey strips of Naive and Coalesced in Fig. 4), and this step removes it. The scan no longer waits for reads: the surviving points of a page form a page candidate , whose read is submitted when all points of a page have been scanned. After each batch, the search polls for completed reads without blocking and harvests them ( 6○ in Fig. 2): every member is re-screened against the current dist 𝑘 , and those that pass are re-ranked. When the last cluster has been scanned, the search keeps harvesting until every outstanding read returns, i.e., the drain ( 7○ in Fig. 2). As dist 𝑘 may have tightened since the read was submitted, some pages may have been fetched for nothing, which Table 1 reports as waste . How Overlapped performs depends on whether the SSD is saturated. Below its IOPS ceiling (𝑇 =1), the overlap is a clear gain: over Coalesced , throughput rises another 5 .1× at 𝑘 =10 (9 .4× at 𝑘 =100), even though 156 reads are issued where Coalesced needed 81. These 46% wasted reads are acceptable because the benefit of overlapping I/O outweighs the cost of the extra reads. Once the device is saturated ( 𝑇 =64, where the 64 threads together drive the SSD at its IOPS ceiling), additional reads begin to queue. I/O completions slow down, delaying both harvesting and tightening of dist 𝑘 . The resulting stale threshold allows more candidates to survive pruning and triggers still more reads. In our trace, the number of outstanding reads for one query peaks at 677 in Fig. 4b. In this regime a query wastes 83% of the reads and spends 89% of its list-search time in the drain (Table 1). Throughput falls below Coalesced at both 𝑘 (0 .45 × and 0 .84 ×) and, at 𝑘 =10, below even the blocking Naive .

Scheduled . This step bounds the number of reads in flight and moves each read decision from scan time to issue time, when the threshold is tighter. Instead of having its read submitted as soon as the scan leaves the page, a page candidate is deposited in the priority set ( 4○ in Fig. 2), ordered by page lower bound. Reads are issued in that order, keeping at most 𝑄 in flight ( 5○). After each batch, the search polls and harvests as before, and conditionally submits new reads by order of lower bound: (a) if fewer than 𝑄 are in flight and (b) if each candidate lower bound is lower than the current dist 𝑘 .The issuance stops at the first candidate that fails check (b) as the remaining candidates would fail too or the set is emptied. While a candidate waits in the set the threshold keeps tightening, and most candidates are pruned there without a read ( drop column of Table 1). Because Scheduled keeps fewer reads in flight than Overlapped, its threshold is slightly more stalled and more points survive the scan, but many page candidates are still dropped before incurring I/Os. Fewer fetched pages also mean less harvest work, visible in Fig. 4b

## 4.4 𝛼 -Quantile Threshold to Alleviate Drain 

A drainage problem. The drain runs after the last cluster, as no scanning is left to run in parallel with reads. Below the IOPS ceiling (𝑇 =1) reads complete promptly, little remains after the scan, and the drain represents 6–13% of the list-search time (Table 1). Once the device is saturated ( 𝑇 =64), completions slow down (in our traces the median read completes in 186 μs), so fewer reads are issued during the scan under the bound 𝑄 , more page candidates are left when it ends, and the drain takes 21% of the list-search time at 𝑘 =10 and even 73% at 𝑘 =100. 

Full. This pipeline issues fewer reads by tightening the drain’s threshold. Once the last cluster is scanned ( 7○ in Fig. 2), a pending candidate is issued only if it could still place among the best 𝛼𝑘 of the current results, with 𝛼 ∈ ( 0, 1] and 𝛼𝑘 an integer. This means its lower bound falls below the 𝛼 -quantile of the KNNSet . 𝛼 = 1recovers dist 𝑘 and hence Scheduled , and 𝛼 < 1 gives a tighter threshold. The tighter threshold applies only to reading decisions; harvested pages are still re-screened against dist 𝑘 .The threshold comes with a guarantee: with exact re-ranking and valid lower bounds, every point among the true top-𝛼𝑘 keeps its lower bound below the 𝛼 -quantile threshold and is never pruned. In this way, the search guarantees a recall of at least 𝛼 over the points the probed clusters contain. In practice a far larger fraction of the true top-𝑘 survives the 𝛼 -quantile. We measured this in the tightest possible setting on YFCC-100M, with the running KNNSet replaced by the true top-𝑘 so that the threshold is the 𝛼𝑘 -th smallest true distance: at 𝛼 = 0.4, about 85% of the true top-𝑘 neighbors have a lower bound below this threshold and would not be pruned (84 .2% at 𝑘 =10, 85 .1% at 𝑘 =100), against the 40% the guarantee promises, and we adopt 0 .4 as the default. 

Impact on recall and determinism. In the actual search, the recall loss incurred by the 𝛼 -quantile threshold is even smaller than suggested by this measurement, for three reasons: (1) the running KNNSet typically gives a looser threshold than the true top-𝑘 ; (2) only the candidates still pending when the drain begins face the 𝛼 -quantile threshold; and (3) pruning is per page candidate, against the smallest lower bound among its members, so one strong surviving point keeps its whole page. We note that, with exact re-ranking and valid lower bounds, I/O completion order does not affect the top-𝑘 set returned by 

Scheduled (𝛼 = 1), but can affect that returned by Full (𝛼 < 1). In Full , depending on the order reads finish, re-ranking these candidates can tighten the 𝛼 -quantile threshold sooner or later. Thus, I/O completion order can affect which neighbors are retained at ranks (𝛼𝑘, 𝑘 ]. Appendix B shows that the effect of I/O completion order on the returned neighbor sets and recall is low.

Increasing 𝑘 . Figure 6 extends the throughput comparison to

RaBitQ-SSD benefits from the IVF data layout: the candidates to be fetched are more likely to be co-located in the same SSD page than with graph based methods.

The in-memory code. We evaluate several combinations of in-memory representations for the different methods. PipeANN sup-ports both PQ and RaBitQ codes [55], allowing to compare them directly. Running it with 1-bit RaBitQ codes instead of PQ codes, with its disk graph and layout unchanged, lowers throughput by

The on-disk representation. RaBitQ-SSD-fp stores the raw fp32 vector in place of our ex-codes, to match the default storage of the baselines, whereas DiskANN (disk-PQ) replaces the full-precision vector inside each graph node with a PQ code of one byte per dimen-sion. On YFCC-100M, a compressed on-disk representation reduces the pages needed per record from two to one, lowering page reads per query. This improves throughput by 60+% for both DiskANN and RaBitQ-SSD relative to their fp32 variants, and RaBitQ-SSD still achieves 12% higher throughput than DiskANN (disk-PQ). On LAION-100M, fp32 records already fit in one page, so this effect does not apply: at recall 0 .90, DiskANN (disk-PQ) achieves 6% lower throughput than fp32 DiskANN. This, in turn, stems from the quantization error introduced by disk-PQ, which necessitates additional search work to reach the same recall. However, in RaBitQ-SSD, compact ex-codes stored contiguously within inverted lists allow more surviving candidates to share a page read, which yields 15% higher throughput over RaBitQ-SSD-fp. 

Re-ranking precision. With SQ8 and SQ4, we replace ex-codes with 8-bit or 4-bit scalar quantization with residual encoding [11] on both datasets. At recall 0 .90, 𝐵 = 9 and SQ8 have similar throughput, whereas 𝐵 = 5 achieves 1 .32 × and 1 .26 × the throughput of SQ4 on YFCC-100M and LAION-100M, respectively. SQ4 requires more probing and page reads to reach the same recall. This shows that RaBitQ-SSD combines the 1-bit RaBitQ code and the 4-bit ex-code to produce a more accurate representation than just 4-bit SQ4. 

## 5.6 Additional baselines 

SPANN. SPANN partitions the base into a large number of in-verted lists, keeps their centroids in memory, and reads the probed lists from SSD [9]. Figure 10(a) reports the comparison on Wiki-10M. Memory budgets are not matched: SPANN’s in-memory index takes 6 .6 GB against our 1 .1 GB. At recall 0 .90, RaBitQ-SSD delivers 21 .3× SPANN’s throughput, because SPANN reads 870 pages per query, compared to ∼ 38 for RaBitQ-SSD. SPANN fetches whole selected posting lists, while RaBitQ-SSD performs finer-grained SSD accesses. 

AlayaLaser. AlayaLaser [10] is a graph-based index that accelerates distance estimation using PCA and a SIMD-friendly layout that stores neighbors’ quantized codes in each node’s on-disk record. It caches node records in memory. We use the graph parameters specified in §5.1, with beam width 16 and PCA dimension 256. Therefore, for AlayaLaser, there is a throughput against memory usage tradeoff, which Figure 10(b) shows. Under the memory budget matched to our 𝐷 𝑚 = 𝐷 configuration, AlayaLaser caches about 2.8% of the nodes. AlayaLaser achieves 8 ,592 QPS, compared with 28 ,571 QPS for RaBitQ-SSD. Limited cache coverage leaves many node accesses to SSD, with each cache miss reading a two-page node record. To reach RaBitQ-SSD’s QPS performance, AlayaLaser needs to cache ∼ 50% of the nodes (30 GB of memory), at which point the relevance of a hybrid memory-SSD setting becomes questionable.

## 6 Related Work 

SSD-resident vector search. Among graph-based methods, DiskANN [53] sets the pattern most later methods follow: com-pressed codes stay in memory to guide a best-first traversal, while the graph itself resides on SSD. Subsequent graph-based methods reorganize the on-disk layout so that each fetched page serves more of the search [30, 34, 42, 63, 68, 69, 75] and overlap the traversal with asynchronous reads [22, 31]. AlayaLaser accelerates distance computation [10]. A recent study explores this design space [35]. Among partitioning-based methods, SPANN [9] keeps centroids in memory and reads probed lists from SSD; HELMSMAN [27] rebuilds the I/O path on SPDK to saturate its NVMe arrays and uses learned models to choose the probed lists; and OrchANN [8] orchestrates out-of-core search under skewed partitions. Among other methods, LM-DiskANN [44] and AiSAQ [54] move even the compressed codes to the SSD; VeloANN [73] stores RaBitQ ex-codes on the SSD, with its in-memory 1-bit code ordering the graph walk; and SkipDisk [52] prunes reads with a triangle-inequality bound tightened by per-point pivots. Furthermore, some disk-resident in-dexes have been extended to support updates [23, 49, 51, 66, 74]. In RaBitQ-SSD, the in-memory prefix of the 1-bit RaBitQ code gives every point its own bound (§3), and only the pages of surviving candidates are read (§4). 

Vector quantization. A substantial body of work has investigated the quantization of high-dimensional vectors across multiple fields, including machine learning, computer vision, and data manage-ment [2, 5, 14, 16, 17, 19, 20, 24, 28, 29, 38, 45, 56–58, 64, 70, 72]. We refer readers to existing surveys, experimental studies, and textbooks for more comprehensive overviews of related tech-niques [12, 36, 39, 47, 60, 62, 71]. This paper builds on RaBitQ [17], which provides probabilistic bounds on distance-estimation error, and its extension supporting flexible bit budgets [16] (§2.2). In particular, RaBitQ has been integrated with in-memory graph in-dexes [21], made GPU-native [48], and run as a heterogeneous NPU–CPU system [26]. Some recent quantization methods are built on top of RaBitQ: MRQ [67] truncates PCA-projected dimen-sions and quantizes the kept dimensions with RaBitQ; and SAQ [33] allocates bits across segments of PCA-projected dimensions non-uniformly and quantizes each segment with a variant of RaBitQ. Split-RaBitQ instead derives an unbiased distance estimator and a probabilistic error bound from a prefix of the 1-bit RaBitQ code. 

## 7 Conclusion 

We presented RaBitQ-SSD, a partitioning-based algorithm for SSD-resident vector search. Its Split-RaBitQ design retains a configurable code prefix in memory, enabling fine-grained pruning under differ-ent memory budgets. Its asynchronous pipeline overlaps computa-tion with I/O while reducing unnecessary SSD reads. Experiments show that RaBitQ-SSD provides higher throughput, fewer SSD reads, smaller indexes, and faster construction than comparable graph-based systems from the state of the art. It also searches 10 billion vectors using a single server and one NVMe SSD, demon-strating its scalability.

## B Search-Result Determinism 

We examine search-result determinism using the 𝑛 probe selected for Full to achieve approximately 0 .90 recall, keeping the same value for Scheduled. We execute the query workload eight times, three in the original order and five with shuffled query orders. Table 7 compares the returned neighbor sets across these runs. Scheduled is nearly deterministic after accounting for distance ties. Among 10 ,000 queries, only 5 at 𝑘 = 10 and 4 at 𝑘 = 100 return different top-𝑘 results across the eight runs. The argument of search-result determinism assumes exact re-ranking and valid lower bounds. The remaining changes occur near the rank-𝑘 boundary, where the affected candidates have lower bounds above their true distances and the final 𝑘 -th distances in runs that omit them. Such violations reflect the probabilistic nature of the lower bound, also illustrated by the empirical error distributions in §A.4. Although a candidate’s lower bound is fixed across runs, the candidate may be re-ranked before the running threshold falls below that bound, or pruned if tested later. Recall varies by at most 0 .003 percentage points across runs. Full’s output varies mainly in the tail. At 𝑘 = 100, the unchanged-query fraction is 35 .85% for both the entire top-𝑘 and ranks (0.4𝑘, 𝑘 ],compared with 99 .66% for the first 40 positions. This pattern is con-sistent with the 𝛼 -quantile threshold making retention of neighbors at ranks (𝛼𝑘, 𝑘 ] sensitive to I/O completion order. Earlier re-ranking of closer candidates can tighten the threshold before these neigh-bors’ pages are issued, whereas a different completion order may allow those pages to be read. Although I/O completion order affects the returned neighbors, recall remains relatively stable across the eight runs, ranging from 0 .9005 to 0 .9069 at 𝑘 = 100.

## C.3 Parameter Study 

The in-flight budget 𝑄 . Figure 14 reports throughput at recall 0.90 against 𝑄 on YFCC-100M, one line per thread count ( 𝐷 𝑚 = 𝐷 ). When 𝑄 is too small, a thread has too few reads in flight to use the SSD’s internal parallelism. At 𝑘 = 1000, where a query issues hundreds of reads, throughput at 𝑇 = 1 falls to about a third as 

𝑄 goes from 16 to 4; at 𝑘 = 10 the same change barely changes throughput, because the few reads hide behind compute, as the 

𝑇 = 1 timeline of Fig. 4 showed. When 𝑄 is too large, the pops reach deeper into the priority set and commit candidates that a slightly later threshold would have pruned (§4.3). Each such commit reads a page the query did not need: the page is fetched, swept, and re-screened, some of its members are re-ranked, and none of that work would have happened at a smaller 𝑄 . Under a heavy I/O load the excess reads also lengthen completion latency (§4.4), so candidates are committed against a staler threshold and fewer of them are pruned. Past 𝑄 = 16 throughput declines slightly at 𝑇 = 1; at 𝑇 = 64 and 𝑘 = 10 it falls to about a third of its value at the best 𝑄 . The best 𝑄 therefore rises with 𝑘 and falls with 𝑇 , and the deployed rule ( 𝑄 = 16 for 𝑇 ≤ 16, 𝑄 = 8 above) stays within 3 .7% of the throughput at the best 𝑄 at every 𝑇 and 𝑘 measured.
